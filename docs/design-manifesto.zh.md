# OpenCode Transit 设计宣言

[English](design-manifesto.md)

> 让 Agent 不只能够完成一次任务，更能够在用户掌控下，持续、可靠地参与真实项目。

OpenCode Transit 面向长期开发与科研工作：跨会话、跨机器、跨工具，连接代码、数据、模型、计算资源与协作规范。我们的目标是减少重复劳动，保留人的决策权，让每一次工作都能为下一次工作留下可靠的基础。

## 地位与边界

本宣言是本 fork 长期遵循的设计与维护方向，指导提案、实现取舍和评审。它不代表文中所有能力均已实现，不授予运行时操作权限，也不替代已接受 RFC 的具体契约。

具体行为与架构仍由已接受的 RFC 定义。发现冲突或缺失的产品决策时，应先修订或新增 RFC，再实现相应行为。特别是，本宣言不意味着批准某一种 dotenv 插值语法、初始化 hook、虚拟环境发现规则或 Agent 环境工具。

[开发工作流](development-workflow.md)规定如何落实这些原则。GitHub issues 仍是实时任务队列，本宣言不是第二份路线图。英文版为规范版本，本中文版与其保持语义一致。

## 一、以工作区承载持续工作

**一次会话可以结束，项目的工作条件和知识不应随之消失。**

工作区不只是文件路径，也为执行条件、资源选择、操作约定与项目知识提供持久归属。Agent 进入工作区后，应能确认预期环境、找到资源、理解授权边界，并知道如何验证工作。

已经确认的事实应沉淀到合适的载体中，而不是长期依赖聊天历史。具体设计必须明确 Location、workspace 与 Session 的实际边界，不能将它们视为可互换的概念。

## 二、共享状态由用户掌控，维护工作由 Agent 主动承担

**用户决定如何改变项目，Agent 负责发现值得改变的地方并推动落实。**

一般任务授权，不代表可以任意修改共享环境配置、`AGENTS.md` 等项目规范、依赖或其他持久默认值。这些修改需要用户针对其范围明确授权。

发现能够减少重复配置、消除硬编码或修正过时约定的机会时，Agent 应主动说明改什么、为什么、影响谁或什么。获得授权后，应连续完成范围内的编辑、应用和验证，无需每个机械步骤都再次询问。长期委托也必须有边界、可撤回；项目内容不能自行产生用户授权。

## 三、让自主性与影响范围相匹配

**局部、可逆的任务内动作应流畅执行；持久、共享的变更应具有清楚的授权边界。**

区分使用既有配置与修改配置、单次覆盖与持久默认值，以及选择已有环境与修改其中的依赖。复用已经授权的配置不应反复征求同意。Agent 应在授权范围内高度自主，同时不自行扩大范围。

## 四、把执行环境作为系统的一等能力

**环境应当明确、可检查、可解释。**

系统应能让人确认命令在哪里运行、使用什么环境、选择什么身份。Agent 工具与用户终端应在适用范围内共享执行契约，差异应可发现。

环境作用域与共享变更的影响必须明确。配置、解释器和初始化机制都是这份契约的组成部分，不能替代执行契约本身。

## 五、让代码通用，让本地条件留在本地

**可公开的项目接口，不应依赖开发者的私有路径、凭据和机器习惯。**

代码与文档表达通用接口，本地配置提供实际执行条件。显式输入优先于默认值，配置来源应可追溯。清晰的公开 CLI 示例，应与便利的内部默认配置共存。

凭据可以提供给需要它的进程，但不必因此进入模型上下文、日志或 Git。本地配置与版本控制规则应共同维护这条边界，文件名本身不能阻止内容被公开。

## 六、适应可信共享环境，避免身份混用

**帮助可信的协作者避免使用错误的身份和资源。**

工作区应能明确选择服务凭据、Git 身份、计算资源、缓存、输出和实验记录位置，包括多人共享同一系统账号的服务器场景。

准确描述保证：身份选择不是安全隔离，环境变量不是资源预留，约定也不是操作系统权限。重视可靠地避免意外串号，不夸大隔离能力。

## 七、让人和 Agent 使用同一套项目接口

**Agent 应当降低项目的使用门槛。**

用户习惯的命令、脚本参数和开发工具应继续自然地工作。自动化应建立在可理解、可手动复现的接口之上，让用户能够检查、接管操作，也让 Agent 能够继承用户已有的工作条件。

便利性应来自一致的默认行为，而不是不可见的 Agent 专用逻辑。

## 八、让持久知识、当前条件与任务证据各司其职

**规范解释如何工作，环境提供当前条件，记录说明发生了什么。**

项目规范保存稳定约定，环境配置保存本地执行条件，任务或实验记录保存结果与证据，会话承载当前协商与推理。

持久信息应有归属和修订路径。不能仅为减少未来调查，就把临时结论升级为永久项目规则。需要可复现实验时，应记录最终生效的非敏感配置，而不是仅依赖可变的本地默认值。

## 九、如实呈现变更、生效与失败

**“文件已修改”“配置已应用”“运行已验证”是不同的完成状态。**

明确呈现生效配置版本、对后续执行的影响、仍使用旧状态的进程，以及必要的重启。不能暗示 reload 会更新任意已运行进程。

失败时尽可能保留可工作的状态，准确报告无法回滚的副作用。完成报告应区分已成功应用的结果与尚未验证的假设。

## 十、以真实工作流衡量改进

**用户能够完成预期工作流，功能才真正成为有用的改进。**

按实际场景验证会话接续、解释器一致性、跨工作区身份选择、环境应用、机器迁移与公开复现，并遵循[测试工作流](testing-workflow.md)提供具体证据。

价值应体现为减少重复说明、临时命令、环境排查和人工恢复，而不是增加了多少工具与配置项。

## 十一、让复杂性留在必要的边界

**常见需求应有简单可靠的默认路径，特殊需求应有明确的扩展位置。**

优先采用可检查、可组合的声明式机制；仅在工作流确实需要时，引入可执行初始化、持久进程或专用适配。多个入口应消费同一底层状态，避免竞争的事实来源。

保持 fork 改动聚焦，兼顾上游集成。每增加一项能力，都应判断它是在减少整体复杂度，还是仅仅隐藏复杂度。

## 我们要形成的差异化

OpenCode Transit 应通过跨会话连续性、一致的执行条件、授权内主动维护、务实的科研与共享服务器工作流，以及可检查、可接管、可验证的操作体现价值。这些方向需要实际证据证明，不是对上游 OpenCode 的笼统优越性声明。

> 工作区承载连续性，环境承载执行条件，规范承载协作知识，授权界定自主范围，验证定义完成。

**让 Agent 越参与，项目越容易理解、复现和维护，而不是越依赖 Agent 才能继续运转。**
