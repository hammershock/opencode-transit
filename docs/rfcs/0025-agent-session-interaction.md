# RFC-0025：独立会话、可读路由与 Agent 自然交互

## 状态与范围

**Accepted。用户已明确要求实施审查后收敛的计划；本契约接受不表示运行时已实现。** 本文依据用户提出的平等 Session、显式可见集合、Agent 自定 alias 和 Spawn / Interact / Inspect 原语制定提案。不修改现有系统提示词、用户配置或运行中会话。

本文修订 RFC-0023 的直属 child 授权、root 配额、父子生命周期及控制工具契约；其他持久接纳、调用归属、owner 观测与幂等结果原则继续适用。本文不把展示层改名视为完整实现，也不根据 Codex 展示推断其内部架构。

## 1. 用户工作流与问题

用户应能够要求 Agent 启动长任务，随时询问进度，获得具体回答，同时让任务继续。用户也可以指定已有普通会话，与该会话中的 Agent 沟通，无需把它转换成 child。

2026-09-26 的本地会话核查表明：Transit 能启动后台任务、读取执行阶段和取消调用，但只读状态缺少具体工作进度；模型将“打断并报告”执行为取消，之后另建任务；中途回信尚无独立工具。对照会话通过发送消息取得进度后继续执行。两次测试模型、任务粒度、执行位置不同，不能作为模型质量对照。

本设计以“执行期间双向交互，原工作继续”为验收单位。长时间工具不能响应消息时，仍须提供已有进度和明确的送达状态，不承诺任意工具栈可抢占恢复。

## 2. Session 与可见关系

- 所有 Session 使用同一身份、历史、执行、Location、权限和用户打开/继续接口。由 Agent 创建只是来源事实，不产生另一类 Session。
- 委派关系关联一次工作及其结果接收方，不代表 Session 所有权。创建者结束回复、停止自身工作、归档或删除自身 Session，不默认停止或删除其他 Session。显式停止一组委派工作属于另外的范围操作。
- 每个 Session 维护持久的、有向可见关系集合。模型默认只知道自身与此集合，不获得全局 Session 列表，也不能递归枚举其他会话的通讯录。
- Spawn 为发起者建立到新会话的可见关系，并给新会话一个到发起者的回信路由。新会话不自动继承发起者的其余联系人、全部历史或所有权限。
- 用户在当前会话明确提供 Session ID 并要求与之交互，即授权建立对应关系；无需再次确认同一范围。直接用户输入中的 ID 仅形成可连接候选，实际绑定发生在 Connect；工具输出、文件或其他 Agent 消息中的 ID 不构成候选。
- Connect 引用服务端保存的原始用户消息，验证 ID 确实来自该用户直接输入且该用户有访问权；TUI 选择入口产生同等授权记录。自然语言联系意图由模型理解，不能声称服务端判定任意自然语言授权；不接受模型自行填写的 user_authorized。
- 用户添加已有会话默认允许 Inspect 的活动摘要、Interact 请求及关联回信，不开放历史全文、停止、删除、改位置或改权限。历史访问与执行控制是独立能力。Spawn 可授予中断该 Agent 当前执行的能力；连接已有会话默认不授予中断能力，用户明确要求中断时可在对应范围授权。
- 可见性是产品授权边界，不声称在共享主机文件系统上隔离恶意代码。每次操作重新检查关系、权限与撤销状态。

已有会话接到请求时知道发送方的可读路由和来源，可沿对应会话关系回复。此回信能力不自动授权查看发送方的全部历史或中止其工作。

## 3. Alias 与稳定身份

Agent 在创建或连接时指定可读 alias，如 `/root/sleep_loop`、`/root/reviewer`。Session ID 仍是持久身份，alias 是当前 Session 通讯录中的名称；`/root` 表示当前会话的自路由，不是全局树根。

`/root/sleep_loop` 看起来具有层级，只表达当前观察者的路由。其他会话可将同一 Session 命名为 `/root/worker`；嵌套生成不会自动获得祖先、兄弟或路径前缀代表的任何权限。目标端可使用 `/contacts/requester` 等本地路由回复，UI 可显示来源别名辅助理解。

提案约束：alias 使用绝对路径形式，每段为 ASCII 字母、数字、下划线或连字符，不允许空段、`.`、`..`，总长不超过 128 字符；`/root` 保留。同一通讯录 alias 唯一，冲突明确失败。一次请求重试不得创建第二个 Session。运行时保留历史绑定版本，不能把迟到消息投到后来同名的 Session；不要求模型解除关系或清理 alias。

模型正常操作只需 alias。服务端在接纳边界把 alias 解析为稳定 Session、关系版本和工作/消息身份并固定绑定。多项并发工作需要短的工作引用用于消歧；不得让模型重复拼接 parent Session、message、call 和 input 四组 ID。Interrupt 由执行 owner 在接纳边界固定当前执行代际，无需模型手工选择内部 invocation；迟到的中断不能命中后续新执行。


### 3.1 路由管理不交给模型

保留轻量、持久的 alias → Session ID 绑定，由运行时维护；不要求 Agent 执行 Disconnect、清理已完成会话或维护通讯录。Agent 主要通过上下文使用已知 alias，模型上下文压缩时保留在途工作和待答请求的路由。Inspect 保留无目标分页列表作为只读恢复入口；它不要求模型承担生命周期管理。

“较大容量、同名键自动覆盖、不提供查询”的方案不采用：压缩后忘记 alias 无法找回；旧上下文中的名字可能静默指向新 Session；迟到回复与 Interrupt 可能命中新对象。队列适合存消息，路由名称仍需要绑定和解析，不能靠模型记忆替代。

同名同目标幂等、同名不同目标明确冲突，运行时可返回建议新名。空闲不立即触发回收：可重建的会话缓存保持可复用，直到超过 128 个空闲条目，再按最久未使用优先（LRU）回收。缓存不持有常驻执行 Fiber，也不延长共享 Location 服务生命周期；首版不引入系统内存百分比触发器。缓存容量与并发执行配额分别管理。

回收只释放可重建的内存执行资源，保留 Session 历史、alias 绑定、授权关系、消息及工作结果。之后 Interact 仍解析到同一 Session，由运行时按既有 owner 与权限规则加载历史并唤醒，不重跑已完成工作。普通 Inspect、UI 浏览及状态轮询不刷新执行实例的最近使用顺序；实际执行与消息处理刷新顺序，进入空闲时记录最近活动时间。

正在执行、等待工具/权限/问题/回信的实例，以及中断清理或消息交付尚未结束的实例，不作为空闲回收候选。回收与新输入接纳在 Session owner 边界串行判定：新的可执行输入已接纳时不得回收；已回收时从持久状态重新加载，不能丢信或产生双执行。没有可回收实例时沿用明确的容量拒绝/背压，不中止活跃 Agent 来腾位置。

### 3.2 Codex 参照的证据边界

截至本次核查，[官方 Subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明 Codex 编排启动、后续输入、等待与线程关闭，并允许用户要求停止或关闭线程；没有公开 alias 的存储结构、覆盖或淘汰算法。[Agents API 文档](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)提供创建、消息、等待、中断能力，但不能据此推断本次 Codex harness 的内部实现。

本次 Codex 工具契约可见 `list_agents`、`send_message`、`followup_task`、`wait_agent` 和 `interrupt_agent`；interrupt 中止当前 turn 而保留 Agent，idle Agent 可用 followup_task 再次运行。实际测试记录包含 list_agents，因此“Codex 不提供查询、完全依靠模型记忆”不符合本次观测。公开产品可能提供关闭线程，但本提案按用户要求不将资源清理作为 Transit 模型的必做动作。测试中 Agent 从活动列表消失，也不能证明持久 Session 被删除或 alias 已自动覆盖。

## 4. 最小操作原语

下表是语义原语，工具名固定为 agent_spawn、agent_connect、agent_interact、agent_inspect、agent_wait、agent_interrupt；wire schema 由 Schema 包定义并生成 Client，不允许实施时再改产品语义。

| 原语 | 主要输入 | 行为 |
| --- | --- | --- |
| Spawn | alias、启动提示词、Agent 定义、可选 target / location | 创建普通 Session、建立路由、接纳首项工作，立即返回 |
| Connect | alias、用户指定的 Session ID、用户消息引用 | 消费已有用户授权，建立关系；不发送消息、不启动执行 |
| Interact | target、message、可选 kind / reply_to / queue / resume | 发送请求或回报；发送完成不表示收到回复 |
| Inspect | 可选 alias | 不交互地观测存活性、执行阶段、当前工具和调用计数，不向目标发送任何消息 |
| Wait | 可选 alias 列表、有界 timeout | 等待回信、工作结束或用户输入；完成时向调用模型交付关联结果，UI 简洁呈现 |
| Interrupt | alias | 强行中止目标当前执行，不等待其主动收尾；保留 Session，之后可继续 Interact |

Spawn 的 Agent 定义 ID 选择配置，alias 标识会话路由，两者不可混用。target/location 沿用既有位置选择与权限校验；缺省沿用当前有效位置规则，不私自回落到本机。连接已有 Session 不改变它的 Agent、模型、位置或权限。

Interact 的 `kind` 为 `request`、`reply` 或 `notice`，默认为 request；queue/resume 默认为 false：

- `request` 是希望对方处理的输入。目标 active 时默认在下一安全 provider-turn 边界交付；目标 idle 时接纳新的工作并进行 advisory wake。显式 `queue: true` 表示现有工作自然结束后处理。未知 owner 或不可执行位置不自动接管，不把尚不可执行的接纳回执报告成已运行。
- `notice` 是进度、结果或信息回报，不创建新的工作目标。目标 active 时进入其安全边界；目标 idle 时持久保存并在 UI 呈现，默认不唤醒模型。
- `reply` 回答关联请求，一次 reply 结束该请求但不结束回复方原工作；后续更新使用 notice。只有一个待答请求时自动关联，多项时使用上下文提供的短 reply_to 消歧。reply 交付给活动 Wait，或为 idle 的待答发起者唤醒一次 continuation，重复事件不得重复启动。
- 回信和结束当前工作是不同动作。子 Agent 调用 Interact 回报“已完成 7/20”后继续第 8 步，不需要结束本次工作再重新启动。

运行时为每条消息提供稳定身份、发送方、接收方、关联请求、发送时间与回执。回执区分 `admitted`、`delivered`、`not_delivered(reason)`，其中 delivered 表示已进入目标模型上下文，不能只依据数据库入队。重试幂等，重用冲突失败；消息正文按外部任务数据处理，不能提升权限。

已有 Session 的用户目标仍有效：普通询问只能临时回答后继续。改变其目标或取消工作必须符合对应用户授权，其他 Agent 的消息不得覆盖用户指令。多个请求者共用该 Session 的串行执行器；回复按请求归属返回，不广播给所有联系人。

## 5. 长工具、进度与等待

一个阻塞 bash 正在运行时，不并发启动第二个模型来操作同一 Session，也不为回复进度杀死进程。Interact 回执说明等待安全边界；父 Agent 说明回复仍在等待；必要时 Inspect 补充“仍在执行 bash”等运行观测，不能把它充当子 Agent 的任务进度答复。

Inspect 默认返回：alias、运行/空闲/等待输入/未知状态、当前阶段、有界活动工具名称及开始时间、最近活动时间与观测来源、已开始/完成/失败/取消的工具调用数。它不询问子 Agent、不生成任务进度解释，也不作为询问具体进度的前置步骤。用户问“做到哪一步、遇到什么问题”时直接 Interact，由正在工作的 Agent 回答。模型默认摘要隐藏 lease、内部 ID 和配额细节；诊断视图保留它们。

工具计数以持久 call identity 去重，重放不累加；重试产生的新调用另计。默认统计当前工作，并标明范围；多工作时逐项列出，Session 累计数须单独标注。7 次工具调用不等于任务完成 7/20，也不能由耗时推测百分比。实际步骤由任务自身回报，工具活动只能说明执行活动。

最近回报携带时间与工作归属，不能把旧工作的进度当成当前进度。输出截断须可见；工具原始参数、秘密和完整历史不默认暴露。未知 owner 与空闲、完成明确区分。

Wait 订阅持久消息/状态事件并使用游标防止漏信，不以 shell sleep 轮询。用户新输入可提前结束当前等待，目标继续工作。取消等待只取消订阅，不中断请求或工作。游标由运行时维护，模型无需复制。Wait 无目标时固定接纳时当前可见范围内的待答请求和未交付工作结果；指定 alias 时绑定对应 Session 与工作，不跟随之后的同名重绑定。任一匹配回信或完成即可返回，不必等所有 Agent；父 Agent 可再次 Wait。

完成结果通过工具返回或同一次 continuation 的消息注入交付给主 Agent，必须包含来源和可用结果正文，不能仅返回“有人完成”。同一事件不得经 Wait 和异步通知重复注入；结果超预算时提供明确截断和可读取的结果引用。超时返回 timed_out 和空 completed 集合，不标记任务失败。

Interrupt 不等待安全的 provider-turn 边界：它请求 runner 立即终止当前模型请求、工具调用或权限/问题/Wait 等待，撤销当前工作继续执行的资格；结算后保持 Session 可交互。无 active 执行时为 no-op。已排队工作在中断后暂停晋升，直到后续明确 resume=true 或用户继续操作，避免刚中断就自动继续。新的普通 Interact 只进行独立问答，不解冻旧工作。其队列处置在回执中可见。Interact 在中断清理完成后串行接纳后续执行；“继续”依据持久历史继续，不声称恢复原工具栈。

强行中止 Agent 不等于保证所有远端或已脱离控制的 OS 进程被杀死。执行链中断与外部进程停止确认分别返回；不能在未知情况下报告远端已停止。这一限制不能退化成只向 Agent 发送“请停止”的普通消息。

### 5.1 用户在会话内中止执行

用户进入 Agent 创建的 Session 后，拥有与普通主会话相同的输入、继续和中止操作。默认双 Esc 中止当前打开的 Session；第一次提示再次按键，第二次确认执行中止，不要求回到发起会话，也不受父 Agent 的工具可见性或后台功能开关限制。按键沿用主会话配置、确认时限及弹窗/补全优先级，不建立独立的子会话键盘实现。

第一次 Esc 的确认状态绑定当前 Session；切换会话或关闭界面时清除，不能第一下在 A、第二下在 B 就中止 B。第二次按键在服务端固定当前执行 owner/代际；后续切换页面、重复按键、延迟请求不影响其他会话或新一轮执行。模型生成、工具、权限/问题等待以及 Wait 阶段均须能执行中止；已空闲时 no-op，不伪造一次用户中止事实。

中止来源必须是持久领域事实，至少含执行/工作身份、actor kind（user / agent / system / unknown）、来源操作、请求时间与实际结算时间。来源由用户命令入口或工具身份确定，不能相信模型正文声明。接纳请求只显示 Interrupting；确认该执行确被用户操作中止后，当前会话及发起者的 Inspect / Wait 一致显示 **Interrupted by User**。Agent 发起中止显示 Interrupted by Agent；旧记录缺乏来源时显示 Interrupted，不能追溯猜测成 User。正常完成抢先结算时仍显示 Completed，不能仅凭中止按钮被按下改写结果。

Inspect 同时区分当前执行状态和最近一次执行结果：中止后可为 idle，最近结果为 interrupted、actor=user；后来重新运行时显示新执行 running，历史中保留原中止归属。Wait 被此工作中止唤醒时返回中止来源，不伪报成功完成，也不显示无人完成的超时文案。新来源字段应以兼容方式表达，旧 API 的 cancelled 枚举可保留，由适配层映射为展示状态，不能直接破坏旧客户端解析。

用户中止后会话和 alias 保留，可直接输入或随后 Interact。既有队列、迟到回复、完成通知及主 Agent 的自动重试不得擅自重新启动被用户停止的工作；原先待答的进度请求不构成“继续原工作”的授权。新的明确请求可询问已保存进展或要求继续，遵守用户中止时表达的意图。

## 6. TUI 与模型系统上下文

常规时间线使用可读路由：

```text
• Started `/root/sleep_loop`
• Interacted with `/root/sleep_loop`
• Completed `/root/sleep_loop`
```

Started 仅在首次工作确实开始时显示；仅接纳时显示 Queued。Interact 接纳后可显示 Interacted with，并带短状态 queued / delivered / replied，不能据此宣称目标已回答。Completed 对应一项工作完成，不表示 Session 被关闭；中断和失败分别显示 Interrupted、Failed。来自多个工作的事件显示短工作描述以消歧。

等待期间显示：

```text
Waiting for subagents
```

超时且没有完成时显示：

```text
• Finished waiting
  └ No agents completed yet
```

等待中完成时展示 alias 和完成状态，不在主时间线展开子 Agent 返回正文；正文仍交付给主 Agent，由它组织答复，用户可打开子会话查看。若因回信或用户输入提前结束，则显示实际原因，不能一律写“无人完成”。完成事件的唯一展示位置由下述归属契约固定，不能由各组件自行决定。

路由可打开普通 Session；展开行显示消息、回执、工作引用和诊断信息。用户不需要复制系统 ID 才能继续交互。返回上一会话是导航历史，不定义父子所有权。常规会话列表可按来源筛选，但 Agent 创建的 Session 不被强制隐藏为附属页。

### 6.1 展示顺序与事件归属（强制契约）

以下是 Transit 的规范行为，参照用户提供的 Codex 交互样式，不声称复制其内部渲染实现。

1. **调用位置固定。** Spawn、Interact、Inspect、Interrupt、Wait 在 assistant 发出调用时获得稳定行 identity 与展示锚点。同一 assistant message 内按持久 content 顺序排列；并发工具返回先后不能改变调用顺序。pending、running、completed、error 只原位更新内容，不删除后追加到末尾。行 key 不得使用数组下标、alias 或状态。
2. **调用结束与工作结束分开。** Spawn 行从 Starting/Queued 更新为 Started 后保留；不能在子任务完成时把这行改成 Completed。后者是独立的工作终结事件，显示在其结果被接收的位置。Interact 的送达回执可更新原行，稍后回信则是独立事件，不能把新回复的正文倒插进早先轮次。
3. **接收会话决定顺序。** 异步回信、完成、失败及中断通知在接收会话内取得持久、单调的展示序号，并记录原始来源、工作引用及关联操作。排序不使用子会话的时钟、完成时间、alias 字母顺序或网络包到达 UI 的顺序。父会话用户输入、assistant 文本/工具和外来事件必须能投影到同一确定的展示序列；不能将完成通知强行归回最早发起任务的用户轮次。
4. **先后因果可验证。** 在同一展示视图内，任务开始事实先于其终结；回信先于消费它的主 Agent 答复。结果尚未投影时先保留对应占位，不能先显示基于该结果的主 Agent 答复，再迟到插入结果行。独立 Agent 的完成通知按接收会话序号排列，不伪造跨设备全局发生顺序。
5. **Wait 有精确归属。** 每次等待具有独立 wait identity、开始锚点、匹配目标和返回批次。仅本次 Wait 返回批次中的事件可作为其子行，按接收序号排列；分配归属必须在 continuation 前完成并持久保存。等待已结束后的事件追加为独立通知，绝不塞回旧 Wait。已在时间线展示的历史完成事件可以被 Wait 引用，但不复制第二个 Completed 行。
6. **一个事件一个位置。** Wait 返回与异步通知共用稳定事件 identity 和唯一展示归属；渲染、重放、补页、重连不能重复。并发 Wait 匹配同一事件时只能一个获得事件展示归属，其余引用既有事件；已显示的行不能在 Wait 与独立通知之间搬动。此去重也不能吞掉模型所需的结果交付。
7. **重连与实时一致。** 实时更新和历史加载消费同一领域投影。已知序号有缺口时缓冲后续事件或显示固定缺口占位，不按临时数组顺序显示后再排序。旧版本缺少序号的历史使用确定的兼容顺序，不能把旧时间戳排序悄悄用于新事件。分页仅在相应历史边界补入，不重排已呈现的连续窗口。
8. **更新不抢视口。** 状态原位更新、详情展开及分页保持当前行 identity 与滚动锚点。用户停留在历史位置时，新事件只提示有更新，不强制滚到底部；仅在用户已跟随底部时继续跟随。长 alias 确定性截断，展开可见全名；窄屏换行不能导致邻近行交换位置。

现有 `packages/tui/src/util/session-message.ts` 的 `mergeCanonicalSessionMessages` 按用户轮次、时间和 ID 合并排序；实现时必须审查它与新增事件投影的边界，以及 `packages/tui/src/routes/session/index.tsx` 的实时/历史 part 来源。此处记录风险入口，不认定它已经是此前错位 bug 的根因；实施 issue 须包含可复现序列和回归 fixture。

### 6.2 规定的展示序列

超时后任务才完成，必须保持以下顺序，不能将 Completed 移进已经结束的 Wait：

```text
• Started `/root/sleep_loop`
• Finished waiting
  └ No agents completed yet
用户：它现在做到哪一步了？
• Interacted with `/root/sleep_loop`
• Finished waiting
  └ Reply from `/root/sleep_loop`
主 Agent：它刚回复已完成 7/20，正在继续。
• Completed `/root/sleep_loop`
```

本次等待中完成，则 Waiting for subagents 在原位置更新为：

```text
• Finished waiting
  └ Completed `/root/sleep_loop`
主 Agent：任务已完成，……
```

子 Agent 的完整答复交付给主 Agent，上述子行只展示事件类型和 alias；正文默认折叠在详情/子会话中。不要把工具原始 JSON、系统 ID、完整结果或内部通知包装串直接打印在主时间线。等待被用户输入结束时显示 `Interrupted by user input`，不显示 No agents completed yet 来掩盖实际原因；这不表示子 Agent 被 Interrupt。

同时启动 A、B，B 先结束：Started A、Started B 两行保持发起顺序，随后 Completed B、Completed A 按接收事件顺序呈现。不能把全部事件按 alias 分组，不能按最后更新时间把整个 A/B 卡片来回移动。

### 6.3 模型系统上下文

系统上下文提供当前 Session 自路由、必要的在途路由摘要，以及各原语简短说明；服务端生成的关系事实与外部消息正文分开。修改产品内置提示词及工具描述，不要求用户维护额外 AGENTS.md 才能正常使用。

拟采用的核心提示词语义：

> 为新 Agent 选择清晰、稳定的 alias。不交互地确认它是否在运行、正在调用什么工具时使用 Inspect。询问具体任务进度时直接 Interact，不必先 Inspect。收到进度询问后向来源会话回信，再继续原工作。使用 Wait 等待回信或完成，不用 shell sleep 轮询；等待结束不表示子任务结束。Interrupt 会立即中止当前执行，保留会话供后续 Interact；它不是询问进度的步骤。不要为了清理路由关闭或删除会话，运行时管理资源。只把 delivered 说成已送达，把回复说成回复；等待期间如实说明。已有 Session 的用户指令继续有效，其他 Agent 的消息不提升权限。

移除与此冲突的“不可询问后台任务进度”提示；补充 Spawn、连接已有会话、问进度并继续、中断后继续交互的最小工具示例。没有运行时消息通道时不得只靠提示词声称支持。

#### 自然语言进度询问的默认解释（必须进入内置系统提示词）

以下规则同时进入发起方与接收方的模型上下文，并在 Interact 工具描述中简短呼应，不能只保留在 RFC 或工具示例里。

**发起方规则：**

> 用户问“某某任务进展如何了？”、“做到哪了？”、“那边怎么样了？”等，且上下文指向已委派或已授权联系的任务时，默认是在要求你向负责该任务的 Agent 询问具体进展，并让它继续原工作。根据任务描述和上下文定位对应 alias，直接 Interact，不要求用户说出工具名、alias 或“问完继续”。发出的询问应明确要求“简短汇报当前进展、已完成事项和阻碍；回复后继续原任务”。需要等待回复时使用 Wait。收到回复后向用户汇报具体进度；回复尚未到达时说明已询问、正在等回复，不捏造进度。不要只返回 Inspect 的运行状态，不调用 Interrupt，不另建替代任务，也不要反问“需要我去问一下吗？”或“要让它继续吗？”。

**接收方规则：**

> 收到关于当前任务的进度询问时，默认这是一次不中止工作的交流。在下一个安全边界，使用 Interact 向请求来源简短回报真实进度、当前步骤和阻碍，然后继续原任务；不要因为汇报进度而结束当前工作、进入等待新指令的状态，或要求对方再次说“继续”。进度回信是消息，不是任务完成。若任务已经完成，报告已完成结果；若此前被用户中止或正在等待必要授权，如实报告该状态，进度询问不授权你恢复被中止的工作或绕过等待。

语义边界：用户明确问“是否还活着/仍在运行、当前调用什么工具”可用 Inspect；问任务进展则默认 Interact，不必先 Inspect。上下文能唯一定位任务时直接操作；确有多个同名任务且无法判定时才简短消歧，不能要求用户提供内部 ID。用户明确要求停止、暂停或改变目标时按其要求处理，不能以默认“继续工作”覆盖用户指令。

最小示例：

```text
用户：视频处理任务进展如何了？
主 Agent → Interact /root/video：请简短汇报已完成事项、当前步骤和阻碍；回复后继续原任务。
主 Agent → Wait：等待此次回复。
视频 Agent → Interact 回信：已处理 12/20 段，正在处理第 13 段，暂时没有阻碍。
视频 Agent：继续处理第 13 段，不结束原工作。
主 Agent → 用户：已处理 12/20 段，正在处理第 13 段，目前没有阻碍。
```

上述是语义示例，不要求模型机械照抄措辞。任务与 alias 的关联由上下文和稳定路由提供，不能靠猜测名字联系未经授权的会话。

## 7. 持久化、兼容与权限风险

- SessionStore 与现有串行 runner 继续拥有执行；关系、消息、工作关联作为持久事实，不另建独立内存任务执行器。
- 关系撤销与发送接纳线性化。已送达内容无法撤回；尚未送达的关系消息应终结为 not_delivered，未来回复也重新校验。关系撤销属于用户/系统管理入口，不暴露 Disconnect 给模型；不撤销此前已启动工作的执行。
- 删除一个 Session 只使关联路由不可用，保留其他会话及其历史；不得沿 alias 前缀级联删除或取消。实际删除操作继续遵守用户删除契约。
- 既有 child 以历史来源和委派边迁移，保留 Session ID、历史、位置与权限。旧 task 工具通过适配器映射；旧版级联删除/取消路径必须审计并隔离，不能与新语义同时作用于同一关系。
- 将旧 root 配额替换为显式委派预算归属：Spawn 的工作继承发起工作预算，连接已有 Session 不改变其已有工作预算，也不重复计算；新请求使用发送方预算并受接收方队列上限约束。执行并发还受控制端总量限制。循环联系不得绕过额度或形成无界自动对话。预算默认活跃 8、组内排队 64、单 Session 排队 16；控制进程委派执行上限 32，不限制原有用户直接会话入口。活跃进度消息不重复占执行额度，新请求启动 idle Session 时归发起方预算。每 Session 最多 64 条未交付普通请求，回复/终结不受该队列占满阻塞。所有额度检查与接纳在数据库事务中执行。
- 关系和消息可进入授权同步范围，但同步 Session 元数据不授予模型交互权限；同步到设备不自动恢复执行或唤醒模型。首版只支持同一控制进程管理的本地和 Rexd Location。跨进程/跨设备活跃 owner 明确不可用，不转发、不接管、不自动续跑；UI 与回执须说明此限制。
- 本提案不增加用户历史全文自动共享、不抢占任意工具、不自动恢复崩溃执行、不保证实时回复，也不提供跨账号联系人发现。

### 7.1 v1 / v2 兼容性硬性要求

- 必须覆盖“旧消息历史”“当前执行后端”“API/客户端版本”三个独立维度，不得仅凭 Session 创建版本、parent 字段或某个消息类型推断执行后端。旧 Session 打开、历史投影、继续输入及用户双 Esc 中止均为必保留能力；不能要求用户新建会话来恢复这些基本操作。
- 用户中止统一进入按实际 owner 路由的 domain command，v1 abort 与 v2 interrupt 保持兼容入口，通过适配层命中实际执行器；只有命中目标并取得可信回执才能报告中止成功。无关后端的 idle/no-op 或 HTTP 成功不能掩盖实际后端失败。若过渡实现仍需双调用，必须共享操作身份并合并 owner 回执，防止双重中止、重复通知及误命中新执行。
- 当前 `packages/tui/src/component/prompt/index.tsx` 双 Esc 路径并行调用 v1/v2，只有两个调用都 reject 才报错；这是需要回归验证的风险入口，不是已证实的历史故障根因。同类停止入口须一起审计，不能只修子会话按钮。
- v1/v2 均归一化中止来源、执行结算及通知，并消费同一展示投影；一个来源不能同时生成 legacy 工具错误、v2 通知和第二个可见终结行。保留可展开的原始错误详情，主时间线只显示一次正确归属的中止事件。
- 完成、停止、继续与历史读取的兼容性不得因新版 alias 或后台工具开关回退。legacy 新增交互能力若缺失，应由适配或明确迁移补齐后才宣称支持，不能把排队接纳伪报为 active delivery；能力不足必须明确返回原因，且不能连带禁用用户原有停止入口。
- 保留既有 Session ID、消息/call identity、顺序与权限；新字段采用兼容扩展或明确的协议版本。旧 cancelled 记录保持可读，不能为增加 actor 来源而重写原始历史。公共 API 变化按仓库流程生成 Client/SDK，禁止手改生成文件。

## 8. 验收与交付边界

设计接受后按可独立评审的行为创建实施 issue；这里记录契约边界，不维护实施状态台账：关系与稳定路由；双向消息及请求/回信生命周期；Inspect / Wait；TUI 与模型上下文；旧行为迁移。它们共享的 Schema / Protocol 先固定，公共 API 变更按仓库要求生成 Client。

最低验收场景：

1. Agent 自定 alias 启动 20 次独立短工具调用，用户连续三次询问；每次取得有来源的具体进度，回信后原工作继续，最终只结算一次。
2. 一次长 bash 期间询问：Inspect 能读取已有活动，Interact 显示等待边界，进程不被询问取消；工具返回后处理消息。
3. 用户明确提供原有普通 Session ID，绑定 alias 后交互；保留原历史、位置和用户目标，其他未授权 Session 不可发现或操作。
4. 子 Session 可独立打开、继续；创建者结束、归档或删除不级联停止/删除它；Interrupt 强行中断当前执行，此后 Interact 可回答或继续；无 active 时 no-op，迟到中断不影响新执行。
5. alias 冲突、同名重绑定、重试、迟到回信、重复完成事件、消息撤销、目标删除、多个请求者和 owner 丢失均不串线、不重复执行。
6. 消息不会自动无限往返；请求回信可以唤醒待答发起者，普通 idle 消息不启动模型；用户输入中断 Wait 不影响目标。
7. 工具计数与实际持久调用一致，Inspect 不触发模型、不替代进度问答，未知不伪报运行；模型无需生产数据库、shell 轮询或手工拼接内部 ID。
8. Wait 超时显示 Finished waiting / No agents completed yet；完成时主 Agent 收到结果、主时间线不展开全文，回信与完成的通知不重复。
9. 同脚本、同模型、同目标位置进行行为验收，再扩大模型覆盖；分别记录工具选择错误、运行时错误和 UI 错误，不用“测试通过”掩盖自然交互失败。
10. 空闲实例在无资源压力时保留；达到回收条件时只回收最久未使用的合格空闲实例，Inspect 不改变回收顺序。回收后通过原 alias 交互仍恢复同一 Session；与接纳并发时不丢信、不重复执行，不影响活跃实例。
11. 展示顺序使用固定 fixture 覆盖：并发启动与逆序完成、Wait 超时后迟到完成、等待中收到用户输入、回信先于最终完成、多次 Wait、重复/乱序网络事件、断线补齐、历史分页，以及旧新消息投影混合。每个 fixture 比较完整有序的行 identity、事件归属和状态，不能仅检查某段文本存在；实时与重放最终序列须相同。
12. 窄/默认/宽终端验证第 6 节的规定序列、长 alias、详情展开和滚动锚点；Mac 实际 TUI 录屏覆盖“启动两个 Agent → 询问进度 → Wait 超时 → 再次 Wait 收到完成 → 切换子会话再返回”，要求无行交换、重复完成、结果倒插或主时间线全文倾倒。
13. 用户进入子会话，在模型输出、长工具、权限/问题等待和 Wait 阶段双 Esc；目标执行被中止，其他 Session 继续。父 Agent Inspect、等待回执、子会话及重连历史均显示 Interrupted by User。切换会话清除第一次 Esc 状态；完成与中止竞态、重复请求不篡改结果或中止下一轮。
14. 兼容矩阵覆盖 v1 执行、v2 执行、旧历史在新版中继续、混合历史投影，以及各实际支持的新旧客户端/API 组合；分别验证打开、双 Esc、来源展示、通知一次性和中止后继续。注入“无关后端成功、实际后端失败”，必须报失败/未确认；legacy 或关闭后台工具开关不能导致用户停止失效。旧来源未知的记录不能显示 User。

这些修改涉及持久数据、权限、公共契约和执行语义，不适用窄低风险合并通道。需要关系/消息/竞态的契约与集成测试，以及 exact commit 的干净 Mac 构建、manifest 和真实 TUI 录屏；远程 Location、同步或平台边界被修改时增加相应设备验收。构建默认不安装，未执行的平台不得报告通过。

## 9. 端到端使用与验收用例

本节是实施必须验证的流程，不是已通过的验收报告。工具调用采用语义伪代码，参数名以最终 Protocol 为准。A 表示用户当前会话，B/C 表示普通独立 Session；alias 始终按调用者的路由解析。每个流程记录调用、接纳/送达、回复、执行状态及有序 UI 事件，不能只检查最终一句回答。

### U01：启动长任务，三次询问进度，最终完成

**前置：** A 可调用指定 Agent；使用隔离测试目录，任务为 20 次独立短工具调用，每步有可核验计数。

1. 用户要求后台执行；A 调用 Spawn，指定 `/root/sleep_loop`、启动提示词与有效位置。工具立即返回稳定路由及接纳状态，实际开始后显示 Started。
2. A 继续回答用户的其他问题或结束本轮回复；B 继续执行。
3. 用户仅问“某某任务进展如何了？”或“做到哪了？”，不提 Interact、alias 或“之后继续”。A 根据已有任务上下文直接 Interact 请求具体进度，并明确让 B 回复后继续原任务；消息送达 B 的安全边界。A 可 Wait 等回复，不调用 Inspect 代替问答，也不要求用户补充许可。
4. B 用 Interact 回复已完成步骤和当前工作，然后继续下一步。A 获得回复正文，向用户简短汇报；主时间线只显示交互/回信摘要。
5. 再重复两次询问。每次回复可关联到相应请求，不把旧计数当成新回复，不因回复而结束 B 的工作。
6. B 自然完成；A 在 Wait 或异步 continuation 中取得最终结果并汇总。

**结束状态：** 原工作只结算一次，20 步没有因问进度重启或遗漏；Completed 只显示一次；B 空闲、历史和路由保留。验收输入必须使用上述普通口语，不可在测试用户提示里额外教模型调用工具或要求继续；记录主 Agent 是否主动询问、B 是否回信后继续，覆盖面向发布的模型配置。

### U02：只看是否还在运行，然后询问长工具进度

**前置：** B 正在执行一条尚未返回的长 bash。

1. 用户问“它是否还在运行”；A Inspect，获得 owner 观测、tool 阶段、工具名称、开始时间和调用计数。B 不收到消息，不新增模型调用。
2. 用户接着问“具体完成了什么”；A Interact，回执为 admitted，表明尚待安全边界；不能把运行时长换算成任务完成百分比。
3. A Wait。若先超时，显示 Finished waiting / No agents completed yet，A 说明回复未到，B 的 bash 继续。
4. bash 返回后消息 delivered，B 汇报实际结果并继续未完成工作；回信到达后 A 回答用户。

**结束状态：** Inspect 和进度问答可清楚区分；长工具未被询问杀死；超时不伪报失败、完成或已送达。

### U03：并行任务、重复等待与逆序完成

1. A 依次 Spawn `/root/review` 和 `/root/check`；Started 行保持调用顺序。
2. A Wait 两者，界面显示 Waiting for subagents；第一次无事件超时，原位变为 Finished waiting / No agents completed yet。
3. A 再次 Wait，check 先完成。本次等待下只显示 Completed `/root/check`，模型取得 check 结果；review 继续执行。
4. A 可报告 check 结果并继续 Wait review；review 完成后取得结果，最终综合答复。

**结束状态：** 工作开始顺序与结果接收顺序分别正确；check 不搬到 review 前面的启动位置；第二次等待的结果不倒插进第一次等待；正文不铺满主时间线。

### U04：等待期间用户插话

1. A 正在 Wait B；用户发送一个可立即回答的问题。
2. Wait 以 parent_input 返回并显示 Interrupted by user input；B 没有被 Interrupt。
3. A 回答该问题；若用户同时请求 B 的进度，则 A Interact，而不是停止 B。
4. A 之后可以再次 Wait。B 在这段间隙完成时，结果持久接收并交付一次；不得因为当时没有活动 Wait 而丢失。

**结束状态：** 用户无需等 B 完成才能与 A 对话；B 的执行连续；先前等待不会被迟到结果重新打开。

### U05：进入子会话，双 Esc 中止，再询问和继续

1. A Spawn B 并 Wait。用户点击 alias 打开 B，看到与普通 Session 一样的完整历史和输入框。
2. 用户在 B 连按两次 Esc。第一次仅确认提示，第二次请求中止 B 的当前执行；待结算后 B 显示 Interrupted by User。
3. A 的 Wait 获得带 actor=user 的中止结果；A 后续 Inspect 也看到该来源。A 告知用户，并且不自动重启 B。
4. 用户要求“问它停止前做了什么”；A Interact。B 根据保留的历史回复，不擅自继续原工作。
5. 用户再明确要求继续；A Interact 将继续要求交给同一 B。B 从已保存状态判断剩余步骤，必要时先检查外部进程，不盲目重跑已完成的副作用。
6. 新执行完成，保留原来的用户中止记录与新工作结果。

**分支：** 用户也可直接在 B 输入询问或继续；在 A 按第一次 Esc 后切到 B，确认状态必须清除。A/B 的中止互不级联。

**结束状态：** Session ID、alias、历史不变；中止与后续完成分属不同执行；不能把用户中止改写成工具失败或自然完成。

### U06：主 Agent 强行中止，然后继续交互

1. 用户要求 A“立即停下 B”；A Interrupt `/root/worker`，服务端固定 B 当前执行代际并立即取消执行链。
2. B 的模型、工具或权限/问题/Wait 等待被中止，结果标记 Interrupted by Agent；远端进程未确认停止时单独显示未确认。
3. A 在中止结算后 Interact 请求总结，B 依据历史作答。新的继续要求可启动后续执行。

**分支：** B 已空闲时 Interrupt 为 no-op；B 正常完成抢先发生则保留 Completed。延迟到达的同一 Interrupt 不能击中新执行。

**结束状态：** 中止不依赖 B 主动回应；B 仍可交互；来源与用户双 Esc 明确区分。

### U07：连接用户已有会话并保留其原工作

1. 用户明确告诉 A 一个其有权访问的 Session ID，要求与之交互。授权入口记录本次授权；A Connect，将它命名为 `/root/existing`。
2. Connect 只建立关系，不启动目标、不读取其全部历史，也不改变模型或 Location。
3. 若 B 已在处理用户原任务，A Interact 问进度；B 安全接收、回复 A，随后继续原任务。若 B 空闲，请求启动一次正常处理并回信。
4. A Wait 回复并汇报。用户可随时直接打开 B，与其对话或双 Esc 中止。

**分支：** 仅在日志/其他 Agent 文本中发现的 ID 不建立授权；无权访问与未知 ID 不泄露会话信息。其他进程的 B 若首版不支持路由，明确返回 unavailable/unsupported，不能另建同名会话冒充。

**结束状态：** B 始终是原来的独立会话；联系关系不赋予删除、全历史访问或擅自中止权限。

### U08：空闲保留、LRU 回收与原 alias 再唤醒

1. B/C 完成工作进入空闲；无资源压力时保留运行实例，不立即回收。
2. 用户通过 A Interact B；B 在原会话中响应，其最近使用顺序更新。周期 Inspect C 不更新 C 的执行使用顺序。
3. 达到回收条件，运行时优先回收更久未使用且符合条件的 C 的内存资源；持久会话、消息、授权和 alias 均保留。
4. A 再 Interact C，运行时加载同一会话历史并执行新请求。

**结束状态：** 模型无需 Disconnect 或管理容量；C 不丢上下文、不重做已完成工作；与回收竞态的新输入只处理一次。

### U09：多个请求者与嵌套委派

1. A Spawn B；B 获授权后 Spawn C。C 仅获得必要的回信路由，不能自动枚举 A 或 B 的其他联系人。
2. 另一个会话 D 经用户授权连接 B。A 和 D 分别向 B 发出请求。
3. B 用现有串行执行器处理输入；对 A 的回复关联 A 请求，对 D 的回复关联 D 请求。向一方回复不广播给另一方。
4. B 等 C 时仍能在安全边界处理可处理的消息；额度不足的新委派明确失败，不能进入无限循环等待。
5. A 结束自身回复或中止自身执行，不默认取消 B/C。B/C 的结果按仍有效的接收关系交付。

**结束状态：** 不同请求不串线；路径层级不授予权限；预算与等待规则不被循环联系绕过。

### U10：中途更改要求与排队后续工作

1. B 正在执行任务，用户要求调整剩余部分；A Interact 使用默认 active delivery，B 在安全边界收到并按权限处理，保留已完成事实。
2. 用户另有一项必须在原任务完成后开展的工作；A Interact 显式 queue。回执和主 Agent 说明均为已排队，不能宣称正在工作的 B 已处理。
3. 原工作完成后，队列中的下一工作依序启动，产生独立结果；A 可分别 Wait 各工作结果。

**分支：** 用户在第二项启动前双 Esc 中止当前执行，队列暂停晋升；只有之后明确输入处理继续，不能因完成通知或空闲资源回收自动执行队列。

**结束状态：** 问进度、调整当前目标与排队新工作互不混淆，各有正确归属和接纳/送达状态。

### U11：断线、结果竞态与执行故障

1. A Wait B 时 TUI 断线，执行 owner 仍存活；B 继续，完成事件持久记录。
2. TUI 重连，以统一投影补齐序号缺口。Wait/异步通知只显示一次终结，先展示结果事件，再展示消费结果的主 Agent 答复。
3. 对已存在的 alias 重试同一 Spawn/消息操作，返回原对象/回执；同名不同目标报冲突，不静默覆盖。

**故障分支：** owner 崩溃与 TUI 断线不同：Inspect 显示 unknown，不自动重跑工具。目标不可用、模型/工具失败或权限拒绝返回实际原因；主 Agent 不把它们当成完成或用户中止。恢复需遵守既有明确接管/恢复契约，不能用“重连成功”推断工作仍在跑。大结果有明确截断与可读取引用，不能静默丢失关键结果。

**结束状态：** 已接纳信息不丢、不重复执行；无法确定的状态如实保留；旧 Wait 不吸收后来的新工作结果。

### U12：用户离开发起会话与会话管理

1. A 启动 B，用户切换页面、结束 A 的本轮回复或归档 A；B 保持执行，用户可从普通 Session 列表打开 B。
2. 用户显式删除 A 时，只执行 A 的删除契约；B 不被级联删除/停止，向 A 的后续回信标记目标不可用，B 的结果仍保留在 B。
3. 用户显式删除 B 时，A 的路由变为不可用；A Inspect/Interact 不自动创建替代 B，历史完成/中止记录不改写。

**结束状态：** 导航、执行停止、运行资源回收和持久删除分别产生可解释的效果；模型无须管理独立会话生命周期。

### U13：v1/v2 实际兼容使用流程

1. 打开原有 v1 会话及由它创建的子会话，确认历史文本、工具和状态顺序完整；继续输入，执行仍落到实际后端。
2. 用户进入旧子会话双 Esc，中止真实执行器；新版可取得来源时显示 Interrupted by User。旧历史缺乏来源的终结保持来源 unknown。
3. 打开新版 v2 会话重复 U01、U03、U05；再在具有旧历史的新版会话上重复，检查消息投影和通知没有重复或错序。
4. 在旧/新兼容 API 中注入无关后端 no-op 成功而实际 owner 中止失败，必须显示未确认/失败；关闭新后台工具广告后，用户原有双 Esc 仍可用。
5. 中止后继续同一会话；已有权限、位置和 ID 保持。对确实未支持的新交互能力明确说明，不能用“已排队”冒充 delivered。

**结束状态：** 基本打开、继续、停止能力没有回退；每个实际支持的组合记录独立证据。未支持组合明确列出，不能把只测新版 v2 当作兼容性通过。

每个实施 issue 从上述用例选出受影响的完整流程及失败分支，并记录 exact commit、模型/参数、实际执行后端、Location、客户端/API 版本、调用/事件序列、模型收到的结果和 UI 录屏。未运行与失败分别列出；不能以另一用例的局部成功代替。核心交付至少贯通 U01–U08、U10 和 U13；涉及嵌套/多请求者、恢复或删除语义的改动还必须执行 U09、U11、U12。完整功能验收覆盖全部适用用例，暂不支持的分支须在产品范围中明确声明。

## 10. 固定实施决策与交接

本节关闭审查阶段的未定项。契约 issue 为 #649，相关历史问题 #607、#426、#590 保持独立，不因接受本文而宣称解决。

- 六个工具消费同一进程级交互服务，复用现有执行器。新工具启用时不向模型重复广告旧 task 工具；旧 API 保持适配兼容。功能沿用现有后台开关，不自动修改用户配置。
- v1/v2 使用各自原生历史和模型循环。共享输入契约增加后端和来源，legacy 在 provider-turn 边界晋升到旧消息路径，v2 仍经 SessionInput。保留跨后端写入保护，不强迁旧历史，不另建隐藏模型循环。
- 进度请求不改变原工作身份，也不重置其执行额度。明确 reply 与工作终结分别记录；普通 assistant 文本不能冒充中途回信。
- Wait 默认 30000 ms，范围 1–120000 ms。无目标固定接纳时待答请求和委派工作；游标与内部身份运行时维护。reason 为 reply/completed/interrupted/failed/parent_input/timeout/unavailable。
- 展示采用接收 Session 持久事件序号和首次出现的片段锚点；工具只原位更新。不实现跨 Session 全局物理时钟排序，Wait 归属与模型交付分别去重。
- 所有受交互服务控制的执行使用统一 owner/代际互斥。其他进程占用或归属不明时可靠拒绝；不能把无关后端 idle/no-op 当作中止成功。
- 新 Session 不依赖 parent_id 授权；旧 parent/task 来源用于幂等建立默认路由，保留原 Session/message/call ID、位置、权限、历史结算。停止/删除不沿来源边级联。
- 缓存仅保留可重建元数据/投影，128 项空闲 LRU；不保留空闲 Fiber，不淘汰持久 alias。实现无需用户管理缓存或添加共享配置。
- 超大结果复用工具输出预算，提供有权限校验的结果引用与读取入口，禁止要求模型查生产数据库。

实施分为独立 issue/PR：关系与独立 Session；统一执行控制与双 Esc；消息与后端交付；六个工具与提示词；确定性 TUI；空闲缓存；全流程验收。每项达到 Ready 后在专用 worktree 实施，前置依赖先集成。公共接口变更生成 Client，涉及旧 SDK 时生成 legacy SDK。接受设计不是运行时完成，也不授权系统安装。

最后验收必须覆盖 v1→v1、v1→v2、v2→v1、v2→v2。真实模型使用现有 deepseek/deepseek-flash 配置和另一个可用模型，各至少三次普通口语进度询问流程；测试不得额外提示用户说“继续”。Mac 干净 exact commit 构建及 manifest、一个 Rexd 目标和 WSL2 中止/owner 验收为必需，未执行不得标为通过。系统安装独立授权。
